# `review-repair/v1`

**Status:** current experimental policy

**Use when:** implementation already exists and the operator wants iterative
independent review and repair against one frozen accepted review question until
no unresolved blockers remain.

**Do not use when:** the accepted review question is missing, false, or still
being discovered; the target head is unknown; or the requested work is really
product/proposal discovery.

The canonical [Milestone Planning And Delivery Contract](../../milestones/README.md)
wins if this policy conflicts with it. This policy does not authorize a phase
transition that recorded workflow state does not permit.

## Hypothesis

The first review-repair trial validated the semantic cycle but failed its cost
shape. The run found and repaired a real blocker without scope drift, then a
fresh reviewer converged. However, low-effort agents still consumed substantial
usage because root/coordinator supervision created many model activations and
kept several repository contexts live.

The v1 optimization target is therefore:

> Preserve fresh independent review and same-context defect repair while using
> the fewest live subordinate contexts and synchronization activations possible.

Optimize in this order:

1. unnecessary actor boundaries;
2. parent/child synchronization turns;
3. duplicated repository/context reads;
4. duplicated validation;
5. reasoning effort after the finding/repair shape is bounded.

## Operator invocation

```text
Follow orchestration policy review-repair/v1 for PR #<number> through final review.
```

Optional operator overrides may narrow the review target or runtime capability,
but do not broaden the frozen review question.

## Hard invariants

1. **One root/executive plus at most one live subordinate by default.**
2. **No coordinator/foreman by default.** The root dispatches directly to the
   reviewer-implementer. Add an intermediate actor only when it demonstrably
   replaces substantial parent synchronization rather than adding another
   context.
3. **One fresh reviewer-implementer per review cycle.**
4. **Keep that reviewer context only through finding -> approved repair ->
   focused validation, then release it.**
5. **A no-blocker cycle is one dispatch -> one terminal receipt -> release.**
6. **A repair cycle is normally two bounded interactions with the same child:**
   review receipt, then approved-repair receipt.
7. **Do not use repeated model-level polling, progress prompts, stdin peeks, or
   sleep/wait loops as the synchronization mechanism.**
8. **Every receipt is exact-head bound.**
9. **Each validation check has one owner.** Parent and reviewer do not rerun the
   same successful validation unless the final head can invalidate it or the
   canonical contract requires it.
10. **Visible cycle receipts / repair ledger are resumable state.** Hidden
    reviewer reasoning is not required to continue the policy.
11. **The root owns exact-head closure and handoff to ordinary final
    acceptance.**

## Core topology

```text
operator
   |
   v
root / executive
   |
   | review packet @ exact head
   v
ONE fresh reviewer-implementer
   |
   | terminal review receipt
   v
root disposition
   |
   +-- no blockers --> RELEASE reviewer
   |                  root exact-head closure
   |                  handoff to final acceptance
   |
   +-- approved repair
           |
           | bounded repair packet
           v
       SAME reviewer context
           |
           | terminal repair receipt
           v
        RELEASE reviewer
           |
      persist cycle state
           |
      next fresh cycle
```

The retained reviewer context is deliberate: defect understanding is reusable
between finding discovery and approved repair. It is not permission to keep the
reviewer alive for general cleanup, integration, waiting, or the next cycle.

## Preconditions

Before starting:

- implementation exists;
- there is one frozen accepted review question / accepted proposal contract;
- the PR/branch and exact target head are known;
- the goal is to remove blockers under that question, not discover new product
  scope;
- the repository's current workflow state permits review/repair.

If those conditions are false, stop and escalate.

## Root / executive authority

The root owns:

- operator goal;
- frozen review question;
- exact head each receipt applies to;
- finding disposition: address / reject / escalate;
- whether a finding mutates scope or contract;
- whether another fresh cycle is required;
- cycle-ledger / resumable state;
- final exact-head closure and handoff to acceptance.

The root should not normally ingest raw test logs, entire diffs, or reviewer
transcripts. Inspect referenced evidence only when a receipt is insufficient,
contradictory, or signals contract ambiguity.

## Reviewer-implementer authority

The reviewer owns:

- independent review of one exact head against the frozen question;
- concrete evidenced findings;
- a bounded repair and validation shape for each finding;
- implementation of only root-approved repairs;
- focused validation of its repair;
- anomaly reporting when repair would require scope/contract authority;
- one terminal review result and, when asked, one terminal repair result.

The reviewer does not acquire product authority by discovering a concern.

## Runtime synchronization gate

Fresh independent review is valuable enough that review-repair normally needs a
child context. The orchestration runtime must therefore be treated as part of
the topology decision.

Preferred capability:

```yaml
runtime_sync:
  terminal_child_result_without_repeated_model_polling: true
```

Use an event/blocking primitive outside model turns when available.

If the runtime cannot deliver a child result without repeated parent model
activations:

1. **do not add a coordinator** to compensate;
2. keep exactly one subordinate live;
3. use the runtime's longest bounded wait / least-activation path available;
4. do not mix progress prompts or repeated repository inspection into the wait;
5. record the unavoidable polling activations as a policy/runtime failure metric;
6. continue only when independent review is still worth that known cost.

Do not pretend a polling-heavy run satisfied the receipt-driven invariant. The
recorded violation is evidence for improving the runtime or collapsing future
agent boundaries where independence is not required.

## Exact-head binding

Capture the target SHA before every fresh review. The reviewer receipt repeats
it as `head_reviewed`.

Before dispatching approved repairs, verify the branch still points to
`head_reviewed`. Unexplained head drift invalidates mechanical use of the old
receipt; inspect the drift and restart/reconcile the cycle explicitly.

After repair, capture `head_after`. The next reviewer is fresh and reviews that
exact revision.

A receipt cannot float across revisions.

## Review dispatch contract

Send only the information needed to answer the frozen question:

```yaml
policy: review-repair/v1
cycle: 1
target:
  pr: <number>
  head: <sha>
authority:
  review_question: <frozen question or ref>
  accepted_cases: <accepted matrix or refs>
  review_guidance: <applicable guidance refs>
prior_state:
  unresolved_findings: []
instructions:
  - review this exact head against the frozen question
  - raise only actionable blockers permitted by current review guidance
  - do not broaden the review question
  - do not implement yet
  - for each finding provide evidence, contract link, repair shape, and validation plan
  - return one terminal review receipt; do not narrate routine progress
return_schema:
  - cycle
  - head_reviewed
  - findings
  - escalation_required
  - evidence_refs
```

Do not replay the full operator conversation or prior speculative reviewer
observations unless they remain authoritative unresolved state.

## Review receipt

Example:

```yaml
cycle: 1
head_reviewed: abc123
findings:
  - id: RR1
    severity: P1
    summary: <contract failure>
    why_in_scope: <frozen-question link>
    evidence: <ref>
    proposed_repair: <bounded repair>
    proposed_validation:
      - check: <focused check>
        owner: reviewer
escalation_required: false
```

A clean cycle returns:

```yaml
cycle: 2
head_reviewed: def456
findings: []
escalation_required: false
outcome: no_blockers
```

The root dispositions findings:

```yaml
address: [RR1]
reject: []
escalate: []
```

Allow at most one targeted clarification when a materially important receipt
field is ambiguous. Repeated conversational clarification means the return
contract failed; redispatch a corrected packet or escalate instead of drifting
into a supervision loop.

## Repair dispatch contract

Before repair, confirm current head still equals `head_reviewed`.

Send approved finding IDs back to the **same reviewer context**:

```yaml
policy: review-repair/v1
cycle: 1
head_reviewed: abc123
approved_repairs:
  - RR1
rejected: []
constraints:
  - implement only approved repairs
  - preserve the frozen review question
  - do not opportunistically address advisory/rejected observations
  - run the focused validation assigned to this repair
  - return scope/contract/ownership anomalies instead of absorbing them
  - return one terminal repair receipt
```

Keeping context warm does not require keeping reasoning effort high. The
reviewer may use deeper reasoning to establish the failure and repair shape;
once the approved repair is deterministic, execute it economically until an
anomaly returns.

## Repair receipt and resumable cycle state

The repair result becomes durable parent-visible state:

```yaml
cycle: 1
head_reviewed: abc123
head_after: def456
findings:
  addressed: [RR1]
  rejected: []
  escalated: []
repair:
  completed: [RR1]
  failed: []
validation:
  - check: <focused check>
    owner: reviewer
    status: pass
unresolved: []
anomalies: []
next: fresh_review
refs:
  diff: <ref>
  validation: <ref>
  review_receipt: <ref>
```

After this receipt, **release the reviewer**.

If the PR uses the canonical `Repair Cycle Ledger`, update it after each
completed repair cycle with the authoritative review receipt, classification,
severity, repair revision, and contract impact required by the milestone
contract.

A fresh session should be able to resume from:

- current PR/head;
- frozen review question;
- exact-head review receipts;
- repair-cycle ledger / compact cycle receipts;
- unresolved findings, if any.

It should not need hidden chain-of-thought, encrypted worker packets, or a prior
worker transcript.

## Validation ownership

Assign each check once.

Typical split:

```yaml
validation:
  - check: focused regression for RR1
    owner: reviewer
    rerun_at_closure: false
  - check: repository-required full suite at final head
    owner: root
    rerun_at_closure: true
```

Do not rerun a successful reviewer-owned focused check in the root merely to
confirm the reviewer ran it. Re-run only when later head changes can invalidate
it, it is part of final-head acceptance, or repository guidance explicitly
requires it.

Reduce deterministic test output to status/count/failing identities and refs.

## Reviewer lifecycle

Keep the reviewer only for:

```text
independent review
      -> root disposition
      -> approved repair
      -> repair validation
```

Then release it.

Do not retain the reviewer for:

- unrelated cleanup;
- speculative improvements;
- PR-description work;
- general integration supervision;
- waiting for unrelated CI;
- final acceptance;
- the next fresh cycle.

## Loop

```text
1. capture exact head
2. dispatch ONE fresh reviewer
3. receive terminal review receipt
4. verify receipt head
5. root dispositions findings

   no valid blockers
      -> RELEASE reviewer
      -> root exact-head closure
      -> handoff to ordinary final acceptance

   valid repairable blockers
      -> verify no head drift
      -> SAME reviewer implements approved repairs
      -> receive terminal repair receipt
      -> RELEASE reviewer
      -> persist cycle/ledger state
      -> start NEW fresh reviewer on head_after

   contract/scope ambiguity
      -> RELEASE reviewer when safe
      -> escalate
```

Fresh context between cycles protects independent re-review. Same context within
one cycle avoids paying to reconstruct defect understanding.

## Root-owned closure

After a fresh exact-head review returns no blockers:

1. release the reviewer;
2. verify the no-blocker receipt names the current exact head;
3. run only required root-owned final-head validation;
4. ensure repair-cycle/resumable state is current;
5. confirm no unresolved escalation or finding remains;
6. hand off to the repository's ordinary exact-head final acceptance mechanism.

A no-blocker review receipt is **not** final acceptance unless the canonical
workflow explicitly defines it as such. Do not launch another worker merely for
this deterministic closure.

## Completion

`review-repair/v1` is complete when a **fresh independent review of the current
exact head** produces no unresolved blockers under the frozen accepted question
and required policy-owned validation is passing on that head.

The next permitted action is ordinary final acceptance/review under the
canonical repository workflow.

It is not complete merely because:

- the repairing reviewer believes its own repair is correct;
- advisory observations reach zero;
- no agent can imagine further improvement.

## Escalate instead of looping when

- the accepted review question is false or incomplete;
- repair requires a proposal amendment;
- safety, schema, ownership, external assumptions, or operator journey changes;
- validation contradicts the claimed repair;
- unexplained head drift invalidates the current receipt;
- reviewer output cannot be made actionable through one targeted clarification;
- operator judgment is required.

Do not escalate merely because a second repair cycle exists when the canonical
contract still permits another cycle against the same accepted question.

## Trial metrics

Measure topology explicitly:

```yaml
orchestration_metrics:
  review_cycles: <count>
  reviewer_launches: <count>
  model_calls:
    root: <count>
    reviewers: <count>
  root_child_turns: <count>
  poll_wait_turns: <count>       # target: 0; record runtime limitation if nonzero
  max_live_subordinates: <count> # default target: 1
  coordinator_used: false
  duplicated_validation: <count>
  exact_head_receipts: true | false
  final_acceptance_done: true | false
  outcome: converged | escalated | failed
```

Token/cost totals are secondary evidence. Cache can make a structurally
wasteful run look inexpensive in dollars while model activations and usage-limit
consumption remain high.
