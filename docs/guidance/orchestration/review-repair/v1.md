# `review-repair/v1`

**Status:** current experimental policy

**Use when:** implementation already exists and the operator wants iterative
independent review and repair against one frozen accepted review question until
no unresolved blockers remain.

**Do not use when:** the accepted review question is missing, false, or still
being discovered; the target head is unknown; or the requested work is really
product/proposal discovery.

The canonical [Milestone Planning And Delivery Contract](../../../milestones/README.md)
wins if this policy conflicts with it. This policy does not authorize a phase
transition that recorded workflow state does not permit.

Apply the shared [orchestration capability gradient](../README.md#capability-gradient)
to every reviewer launch. A bounded review/repair cycle uses the lowest capable
available runtime; in-policy review against a frozen question is in-capability
for that economy tier.

## Hypothesis

The first review-repair trial validated the semantic cycle but failed its cost
shape. It found and repaired a real blocker without scope drift, then a fresh
reviewer converged. However, low-effort agents still consumed substantial usage
because root/coordinator supervision created many model activations and kept
several repository contexts live.

The v1 optimization target is:

> Preserve fresh independent review and same-context defect repair while using
> the fewest live subordinate contexts and synchronization activations possible.

Optimize in this order:

1. unnecessary actor boundaries;
2. parent/child synchronization turns;
3. duplicated repository/context reads;
4. duplicated validation;
5. lowest capable reviewer runtime once a child is justified;
6. reasoning effort after the finding/repair shape is bounded.

## Operator invocation

```text
Follow orchestration policy review-repair/v1 for PR #<number> through final review.
```

## Hard invariants

1. **One root/executive plus at most one live subordinate by default.**
2. **No coordinator/foreman by default.** Add an intermediate actor only when it
   demonstrably replaces substantial parent synchronization instead of adding
   another context.
3. **One fresh reviewer-implementer per review cycle.**
4. **Use the lowest capable available runtime for that bounded reviewer role.**
   In-policy review and approved repair are in-capability for that economy
   tier. A stronger runtime requires remaining uncertainty, a missing
   capability, or demonstrated lower-tier insufficiency.
5. **Keep that reviewer context only through finding -> approved repair ->
   focused validation, then release it.**
6. **A no-blocker cycle is one dispatch -> one terminal receipt -> release.**
7. **A repair cycle is normally two bounded interactions with the same child:**
   review receipt, then approved-repair receipt.
8. **Do not use repeated model-level polling, progress prompts, stdin peeks, or
   sleep/wait loops as the synchronization mechanism.**
9. **Every receipt is exact-head bound.**
10. **Each validation check has one owner.** Parent and reviewer do not rerun the
    same successful validation unless the final head can invalidate it or the
    canonical contract requires it.
11. **Visible cycle receipts / repair ledger are resumable state.** Hidden
    reviewer reasoning is not required to continue the policy.
12. **The root owns exact-head closure and handoff to ordinary final
    acceptance.**

## Core topology

```text
operator
   |
   v
root / executive
   |
   | review packet @ exact head
   v
ONE fresh reviewer-implementer
   |
   | lowest capable runtime
   | terminal review receipt
   v
root disposition
   |
   +-- no blockers --> RELEASE reviewer
   |                  root exact-head closure
   |                  handoff to final acceptance
   |
   +-- approved repair
           |
           | bounded repair packet
           v
       SAME reviewer context
           |
           | terminal repair receipt
           v
        RELEASE reviewer
           |
      persist cycle state
           |
      next fresh cycle
```

Retaining reviewer context is deliberate: defect understanding is reusable
between finding discovery and approved repair. It is not permission to keep the
reviewer alive for general cleanup, integration, waiting, or the next cycle.

## Preconditions

Before starting:

- implementation exists;
- there is one frozen accepted review question / accepted proposal contract;
- the PR/branch and exact target head are known;
- the goal is to remove blockers under that question, not discover new product
  scope;
- the repository's current workflow state permits review/repair.

If those conditions are false, stop and escalate.

## Authority

The root owns operator goal, frozen review question, exact-head applicability,
finding disposition, scope/contract decisions, whether another fresh cycle is
required, resumable cycle state, and final exact-head closure.

The reviewer owns independent review of one exact head, evidenced findings,
bounded repair/validation proposals, implementation of only approved repairs,
focused repair validation, and anomaly reporting when repair would exceed
scope/contract authority.

The reviewer does not acquire product authority by discovering a concern.

## Runtime and capability gate

Fresh independent review normally needs a child context. Prefer a runtime that
can deliver the terminal child result without repeated parent model turns:

```yaml
runtime_gate:
  terminal_child_result_without_repeated_model_polling: true
  lowest_capable_runtime: <runtime>
```

Use an event/blocking primitive outside model turns when available.

After the topology passes that gate, choose the lowest capable reviewer runtime.
In-policy review against one frozen question uses the economy tier by default.
Escalate to a stronger runtime only when the unit still has unresolved
uncertainty, needs a capability the lower tier lacks, or the lower tier already
failed with evidence. Do not keep the reviewer on a stronger runtime merely
because independent review involves judgment.

If the runtime cannot return a terminal child result without repeated polling:

1. do **not** add a coordinator to compensate;
2. keep exactly one subordinate live;
3. use the runtime's longest bounded wait / least-activation path available;
4. do not mix progress prompts or repeated repository inspection into waits;
5. record unavoidable polling activations as a policy/runtime failure metric;
6. continue only when independent review is still worth that known cost.

Do not label a polling-heavy run receipt-driven merely because the reviewer
eventually returned a receipt.

A multi-cycle review-repair run that never uses the lowest capable available
reviewer tier is an orchestration smell and must record why. Do not manufacture
a pointless extra cycle merely to satisfy the metric. In-policy review against
a frozen question is not itself a reason to stay above the economy tier.

## Exact-head binding

Capture the target SHA before every fresh review. The review receipt repeats it
as `head_reviewed`. Before approved repair, verify the branch still points to
that head. Unexplained drift invalidates mechanical use of the receipt.

After repair, capture `head_after`. The next fresh reviewer reviews exactly that
revision. A receipt cannot float across revisions.

## Review dispatch contract

```yaml
policy: review-repair/v1
cycle: 1
target:
  pr: <number>
  head: <sha>
runtime: <lowest capable available runtime>
authority:
  review_question: <frozen question or ref>
  accepted_cases: <accepted matrix or refs>
  review_guidance: <applicable guidance refs>
prior_state:
  unresolved_findings: []
instructions:
  - review this exact head against the frozen question
  - raise only actionable blockers permitted by current review guidance
  - do not broaden the review question
  - do not implement yet
  - for each finding provide evidence, contract link, repair shape, and validation plan
  - return one terminal review receipt; do not narrate routine progress
return_schema:
  - cycle
  - head_reviewed
  - findings
  - escalation_required
  - evidence_refs
```

Do not replay the full operator conversation or prior speculative observations
unless they remain authoritative unresolved state.

## Review receipt and disposition

```yaml
cycle: 1
head_reviewed: abc123
findings:
  - id: RR1
    severity: P1
    summary: <contract failure>
    why_in_scope: <frozen-question link>
    evidence: <ref>
    proposed_repair: <bounded repair>
    proposed_validation:
      - check: <focused check>
        owner: reviewer
escalation_required: false
```

A clean cycle returns:

```yaml
cycle: 2
head_reviewed: def456
findings: []
escalation_required: false
outcome: no_blockers
```

The root dispositions findings:

```yaml
address: [RR1]
reject: []
escalate: []
```

Allow at most one targeted clarification when a materially important receipt
field is ambiguous. Repeated clarification means the return contract failed;
redispatch a corrected packet or escalate instead of entering supervision.

## Repair dispatch and receipt

Before repair, confirm current head still equals `head_reviewed`. Send approved
finding IDs back to the **same reviewer context**:

```yaml
policy: review-repair/v1
cycle: 1
head_reviewed: abc123
approved_repairs:
  - RR1
rejected: []
constraints:
  - implement only approved repairs
  - preserve the frozen review question
  - do not opportunistically address advisory/rejected observations
  - run the focused validation assigned to this repair
  - return scope/contract/ownership anomalies instead of absorbing them
  - return one terminal repair receipt
```

Keeping context warm does not require keeping reasoning effort high. Once the
approved repair is deterministic, execute it economically until an anomaly
returns. Do not upgrade runtime merely because repair follows review; retain the
same lower-tier reviewer context when it remains capable of the approved repair.

The terminal repair result becomes resumable parent-visible state:

```yaml
cycle: 1
head_reviewed: abc123
head_after: def456
findings:
  addressed: [RR1]
  rejected: []
  escalated: []
repair:
  completed: [RR1]
  failed: []
validation:
  - check: <focused check>
    owner: reviewer
    status: pass
unresolved: []
anomalies: []
next: fresh_review
refs:
  diff: <ref>
  validation: <ref>
  review_receipt: <ref>
```

After this receipt, **release the reviewer**.

If the PR uses the canonical `Repair Cycle Ledger`, update it after each repair
cycle with the authoritative receipt, classification, severity, repair revision,
and contract impact required by the milestone contract.

A fresh session should resume from current PR/head, frozen review question,
exact-head receipts, cycle ledger/compact receipts, and unresolved findings. It
must not require hidden reasoning or private worker packets.

## Validation ownership

Assign each check once:

```yaml
validation:
  - check: focused regression for RR1
    owner: reviewer
    rerun_at_closure: false
  - check: repository-required full suite at final head
    owner: root
    rerun_at_closure: true
```

Do not rerun successful reviewer-owned focused validation merely to confirm it
ran. Re-run only when later changes can invalidate it, it is final-head
acceptance evidence, or repository guidance requires it.

## Reviewer lifecycle and loop

Keep the reviewer only for:

```text
independent review
      -> root disposition
      -> approved repair
      -> repair validation
```

Then release it. Do not retain it for unrelated cleanup, speculative
improvements, PR-description work, general integration supervision, unrelated
CI waiting, final acceptance, or the next cycle.

```text
1. capture exact head
2. dispatch ONE fresh reviewer on the lowest capable available runtime
3. receive terminal review receipt
4. verify receipt head
5. root dispositions findings

   no valid blockers
      -> RELEASE reviewer
      -> root exact-head closure
      -> handoff to ordinary final acceptance

   valid repairable blockers
      -> verify no head drift
      -> SAME reviewer implements approved repairs
      -> receive terminal repair receipt
      -> RELEASE reviewer
      -> persist cycle/ledger state
      -> start NEW fresh reviewer on head_after

   contract/scope ambiguity
      -> RELEASE reviewer when safe
      -> escalate
```

Fresh context between cycles protects independent re-review. Same context within
one cycle avoids paying to reconstruct defect understanding.

## Root-owned closure

After a fresh exact-head review returns no blockers:

1. release the reviewer;
2. verify the no-blocker receipt names the current exact head;
3. run only required root-owned final-head validation;
4. ensure repair-cycle/resumable state is current;
5. confirm no unresolved escalation/finding remains;
6. hand off to the repository's ordinary exact-head final acceptance mechanism.

A no-blocker review receipt is **not** final acceptance unless the canonical
workflow explicitly defines it as such. Do not launch another worker merely for
this deterministic closure.

## Completion and escalation

Complete when a **fresh independent review of the current exact head** produces
no unresolved blockers under the frozen accepted question and required
policy-owned validation is passing on that head. The next permitted action is
ordinary final acceptance/review under the canonical workflow.

Escalate when the accepted question is false/incomplete; repair requires a
proposal amendment; safety/schema/ownership/external assumptions/operator
journey changes; validation contradicts the repair; head drift invalidates the
receipt; reviewer output cannot be made actionable through one targeted
clarification; or operator judgment is required.

Do not escalate merely because a second repair cycle exists when the canonical
contract still permits another cycle against the same accepted question.

  final_acceptance_done: true | false

Token/cost totals are secondary evidence. Cache can make structurally wasteful
orchestration look inexpensive while model activations and usage-limit
consumption remain high. Whether capability actually descends to the lowest
capable reviewer tier is also a first-class result.
