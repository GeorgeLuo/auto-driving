# `product-implementation/v1`

**Status:** experimental; awaiting a real frontier implementation trial.

Use when the operator assigns implementation of one accepted frontier proposal.
The proposal settles the outcome and acceptance boundary, not every implementation
choice. This policy consumes that authority; it does not create a substitute proposal.
Canonical [contract](../../../milestones/README.md) wins. Pin immutable
[shared/v1](../shared/v1.md). The specific overrides below govern this policy only.

## Invocation and entry

```text
Follow orchestration policy product-implementation/v1 to implement
<accepted proposal> on <milestone branch>. Deliver ready for independent review.
```

Read the normal router and implementer/task guidance. Run the plan's documented
`workflow.py status --plan <path>` command on the governing milestone branch.
Start only at `ready_for_implementation` with acceptance recorded for the proposal
and any amendments. Resume an existing implementation only when its recorded
`implementation_in_review` state and operator assignment permit the intended work.
Do not start during proposal/amendment review, idle current, or milestone closeout.
Recheck PR, base/head, accepted artifacts, and unresolved findings on resumption.
The implementation PR targets the milestone branch, not `main`.

## Flow and ownership

```text
accepted proposal + current workflow state
  -> root compiles one task packet
  -> one worker delivers a complete representative slice
  -> receipt: contract fits? local implementation decision or escalation
  -> remaining bounded units, if any
  -> root closure: final validation + implementation PR
  -> ready for independent review
```

Root owns scope disposition, unit packets, validation ownership, integration, and
handoff. Workers own their implementation context, permitted design choices, edits,
and focused evidence. Neither inherits proposal, product, or acceptance authority.
One live subordinate, no coordinator, by default. Divide by independently verifiable
behavior/ownership, not one worker per layer or file. Keep a coupled end-to-end slice
with one worker; there need not be a second implementation unit.

## Compile the accepted contract, not another plan

Before edits, persist one compact packet. Reference accepted source rather than
copying the full proposal, milestone history, policies, and raw logs into every actor.

```yaml
policy: product-implementation/v1
shared: shared/v1
packet_revision: 1
identity:
  plan: <path>
  frontier: <id>
  proposal: {path: <path>, pr: <number>, reviewed_head: <sha>, merge: <sha>}
  amendments: []   # refs and accepted identities when present
  implementation: {branch: <branch>, pr: null, base: <sha>, head: <sha>}
contract:
  question: <one accepted review question>
  cases: <accepted cases/matrix ref>
  owner: <named owning boundary>
  constraints: <authority, schema, external assumptions, non-goals refs>
  evidence: <accepted capture strategy, readiness, rendering and validation refs>
discretion:
  open_choices: [] # implementation choices deliberately left open; constraints + owner
  fixed_choices: <proposal constraints to preserve>
runtime:
  root: {requested: <model/effort>, observed: unknown}
  worker: {requested: <model/effort>, observed: unknown}
  synchronization: <supported completion mechanism and fallback>
units:
  - id: A1
    objective: <smallest complete slice of accepted behavior>
    owner: <worker>
    paths: <bounded expected paths; supported dependencies may be discovered>
    validation: [{check: <identity>, owner: A1, rerun_when: <reason or never>}]
    stop_if: <which accepted assumption would be falsified>
closure: {owner: root, checks: <integrated/final-head checks>, delivery: implementation_pr}
next: dispatch_A1
```

Record operational model names/efforts per run; they are not canonical policy SKUs.
The root can be a fresh economical session supplied this packet. Do not assume a
running root can change its own model or that requested runtime proves actual runtime.
A fresh root reloads authority and live identity, not the predecessor's transcript.

## Decisions during implementation

| Discovery | Decision and owner |
| --- | --- |
| Algorithm, internal shape, layout, or interaction detail left open by the proposal | Worker chooses within stated constraints, exercises the public behavior, and records the decision if it affects later work. Do not ask the operator about routine mechanics. |
| First slice disproves a proposed implementation pattern, while the accepted outcome and owner still hold | Root revises only the affected unit/pattern and redispatches. Record the failed assumption; do not reopen the whole plan. |
| Existing supported behavior requires another implementation file within the same accepted owner | Worker reports the path and reason; root reconciles the packet. A file-list change alone is not a new contract. |
| Accepted review question, explicit non-goal, safety/authority, schema, external assumption, owner, exit criterion, or expected handoff must change | Stop dependent implementation and use the canonical amendment/later-frontier route. More reasoning does not grant authority. |
| Human asks for additive behavior while testing | Classify with the canonical HITL guidance; do not absorb it as an internal design choice or let this policy authorize an adjunct. |
| Required external capability is missing | Identify the owner and smallest missing contract; follow the canonical capability-gap route. Do not silently work around the boundary. |

An accepted proposal need not specify the exact code or screen. Conversely, an
explicit accepted product detail is not optional merely because a different solution
seems better. The canonical classification resolves that boundary.

## First slice and remaining work

A1 crosses the actual delivery path: input/public entry, behavior at the owner,
consumer output, and the focused acceptance check. Include registry/wrapper/schema
wiring when applicable. A helper passing in isolation is not proof that the slice
works. Use actual rendered output for a visual/link claim, not just generation success.

Respect the proposal's evidence topology: synthetic/focused proof does not replace
required live evidence; do not start durable live capture before its readiness gate.
Complete the accepted evidence rendering or preserve the operator-owned skip.

If repeated units remain, retain a short pattern: where it applies, procedure,
validation, and what invalidates it. Delegate later units with that pattern and their
own bounded context. Do not manufacture fanout or mechanically preplan every task
before the first slice teaches whether the implementation shape works.

## Capability allocation and synchronization

Use the lowest capable available runtime for compiled mechanics and established
patterns. Root selects a stronger runtime for a concrete unresolved design question,
a demonstrated lower-tier failure, or an explicit operator allocation. Model tier
and reasoning effort are separate; prose is not inherently cheap, and code is not
inherently expensive. After a bounded design decision, return to economical execution.
Do not add a worker simply to report a descent metric or hand off trivial bookkeeping.

Shared-default overrides for this policy:

- Receipt-based delegation is preferred for compiled work when supported. Establish
  the actual synchronization capability before dispatch; do not promise asynchronous
  root resumption merely because a worker can run after the root returns.
- If runtime restrictions force repeated model activations to wait, record the
  limitation and choose direct execution at a capable runtime or an explicit saved
  handoff. This replaces shared/v1's delegation-only default for that runtime case.
  Do not strand active work or claim zero polling. A saved handoff names the worker,
  receipt destination, pending work, and who resumes; it is not completion.
- Root may read the smallest source/evidence needed for an explicit disposition or
  closure concern. This is a bounded exception to shared steering input restrictions,
  not permission to duplicate each worker's repository inspection.

Wait for terminal results rather than inspecting worker files, transcripts, or progress.
Avoid short wait loops and redundant nested wait tools. Process-level CI watching can
avoid repeated status queries, but does not guarantee no model wakeups. Higher-priority
runtime/user-update constraints apply; count any resulting activation honestly.
One clarification per dispatch; repeated ambiguity means recompile or escalate.

## Receipts, failure, and recovery

A worker returns one compact receipt; detailed evidence stays referenced:

```yaml
unit: A1
packet_revision: 1
input_head: <sha>
head_after: <sha>
status: complete # or anomaly / failed
plan_fit: matched
changed_paths: []
decisions: []   # choice, constraint preserved, evidence; only material decisions
validation: [{check: <identity>, revision: <sha>, result: pass, evidence: <ref>}]
unresolved: []
anomalies: []
next: <remaining unit or root closure>
```

Release a completed worker. Before dispatch/publication, reconcile head and changed
files with the receipt; unexplained drift invalidates it. A failed launch can leave
edits without a receipt: isolate and inspect those changes, record unknown completion,
and validate before adopting them. Do not erase useful partial work or retry blindly.
A child completion receipt is not independent review or acceptance.

## Validation, QCA, and root closure

Assign one owner per check in the packet. Focus on accepted consumer/boundary behavior;
justify mechanism tests when needed. Rerun only for changed relevant inputs, an explicit
final-head requirement, or a concrete unresolved concern. Preserve exact commands,
revisions, outcomes, and limits. Do not substitute old passing results for new evidence.

When existing QCA is useful and available at the target revision, use its change
observations to focus inspection: contract changes suggest consumer compatibility
questions; test-effectiveness candidates suggest inspecting the exercised boundary.
Record a material observation's decision and evidence in the receipt, not a new gate.
Missing/static evidence does not establish runtime failure or poor tests. No mandatory
QCA run, score, detector work, or test deletion based on counts. Follow canonical
testing guidance; QCA does not replace accepted tests or product evidence.

Root closure:
1. Reconcile units, decisions, changed paths, and anomalies to the accepted proposal
   and all amendments. Finish scoped integration; do not start another feature.
2. Verify whole-delivery/final-head validation and accepted evidence obligations.
   Reconcile focused receipts instead of rerunning everything at each handoff.
3. Create/update the implementation PR using the repository template: accepted
   proposal references, actual diff/validation, limitations, and real repair history.
   Batch metadata changes where possible; body/review events can rerun CI.
4. Persist the run outcome and hand off ready for independent implementation review.

Stop here. No self-acceptance, merge, milestone completion, frontier advance, or
automatic review-repair loop. Those require the ordinary role/phase assignment.
If the operator explicitly composes a review policy, transition with a fresh exact-head
packet and the same accepted question; implementation completion itself is not approval.

## Run record and experiment limits

Persist setup, packet revisions/material decisions, dispatch/receipt events, validation,
runtime deviations, and outcome in one run directory. For committed audit records use
`docs/synthesis/artifacts/orchestration/<run-id>/`; these are historical evidence,
not workflow authority. Keep protected proposal artifacts and milestone state unchanged.
Reference policy path plus commit SHA and preserve operator overrides in the setup.
Record review/implementation identities separately from a later audit-record commit.

Retain available tool/action results and usage evidence without credentials or private
reasoning. Mark unavailable logs explicitly; a final state snapshot is not an execution
transcript. Git history preserves packet revisions; do not reconstruct missing events
as observed. Archive records when authorized without adding a mandatory PR acceptance gate.

Measure actual model calls separately from dispatches/child launches, and per actor:
requested/observed model and effort, input/cached input/output/reasoning tokens,
wait/status activations, duplicate validations, retries, and outcomes. Missing telemetry
is unknown. Cached input is included in input; reasoning is included in output; do not
sum cumulative counters repeatedly. A zero polling field does not cancel nonzero
wait/status activations. Compare similarly scoped tasks and report evidence/quality
alongside cost. The historical runs motivate this trial; they do not prove a token saving.
