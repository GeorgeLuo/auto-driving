# `ad-hoc-implementation/v2`

**Status:** current experimental policy

**Use when:** the operator requests a bounded implementation/change that has no
preceding accepted proposal and existing repository authority is sufficient to
constrain the work.

**Do not use when:** the task requires product discovery, a new user journey,
an unresolved acceptance contract, a safety/authority change, an external
schema decision, or substantial scope expansion. Escalate instead of silently
turning those decisions into implementation details.

The canonical [Milestone Planning And Delivery Contract](../../milestones/README.md)
wins if this policy conflicts with it. This policy does not authorize a phase
transition that recorded workflow state does not permit.

## Hypothesis

The earlier cuts showed that reducing reasoning effort alone does not make
multi-agent work cheap. Low-effort actors can still consume most of the budget
when many contexts stay live and the parent repeatedly wakes to synchronize.

The v2 optimization target is therefore:

> Resolve uncertainty once, then finish the delivery with the fewest additional
> model activations and context boundaries that preserve correctness.

Optimize in this order:

1. unnecessary actor boundaries;
2. parent/child synchronization turns;
3. duplicated repository/context reads;
4. duplicated validation;
5. reasoning effort once uncertainty is bounded.

## Operator invocation

```text
Follow orchestration policy ad-hoc-implementation/v2 for this change.
```

The operator supplies the requested change and any explicit constraints.

## Hard invariants

1. **One root execution context is the default topology.** Delegation must earn
   its cost.
2. **No substantial implementation begins before a visible delivery manifest
   exists.**
3. **For decomposable/repeated work, prove one end-to-end first-of-kind slice
   before deciding whether to delegate the tail.**
4. **A delegated child must be able to return a terminal receipt without
   repeated model-level parent polling.** If the runtime cannot provide that,
   collapse the actor boundary instead of emulating blocking with supervision
   turns.
5. **At most one live subordinate by default.** More requires an explicit
   parallelism case in the manifest.
6. **No coordinator/foreman role by default.** The root dispatches directly.
7. **Each validation check has one owner.** Do not rerun successful focused
   validation merely because another actor returned it.
8. **Closure is root-owned and explicit.**
9. **Manifest + receipts + repository head must be enough to resume in a fresh
   session without worker transcripts.**

## Core flow

```text
operator request
      |
      v
ONE root -- concentrated planning
      |
      | inspect authority / code / validation
      v
visible delivery manifest
      |
      v
first complete slice when a repeatable pattern is expected
      |
      v
plan/pattern fit?
   /             \
 no               yes
 |                 |
local recompile    remaining work
                   /          \
             small/coupled   delegation candidate
                  |                |
             root continues   viability gate
                                  /      \
                               fail      pass
                                |         |
                           root does it   ONE child
                                           |
                                     terminal receipt
                  \________________________/
                              |
                         root closure
                              |
                    final-head validation
                              |
                         delivery / PR
```

The presence of a repeatable pattern does **not** imply delegation. Once the
root already understands the pattern, keeping the work local may be cheaper
than transferring it.

## Phase 1 — compile the request

Before substantial edits or worker launches, the root reads the applicable
repository guidance and enough code/context to answer:

1. What exactly is changing?
2. Which existing owner, contract, public path, or behavior constrains it?
3. What is explicitly outside scope?
4. What implementation shape best satisfies the request?
5. Which uncertainty must be resolved before routine execution?
6. What focused and whole-delivery validation proves success?
7. Who owns each validation check?
8. What discoveries invalidate the plan or require operator/proposal authority?

Emit a visible manifest. Prose planning that is not reflected in the manifest
is not sufficient policy state.

Example:

```yaml
policy: ad-hoc-implementation/v2
manifest_revision: 1
objective: <bounded operator request>
constraints:
  - <existing authority / behavior to preserve>
non_goals:
  - <explicitly excluded work>
authority:
  - <owner / contract / public path>

units:
  - id: A1
    role: first_of_kind
    objective: <complete representative slice>
    implementation_shape: <expected transformation>
    validation:
      - check: <focused check>
        owner: A1
        rerun_at_closure: false
    escalate_if:
      - <assumption invalidation>

  - id: A2
    role: pattern_following
    objective: <remaining analogous work>
    pattern_from: A1
    owner: root
    validation:
      - check: <focused check>
        owner: A2
        rerun_at_closure: false

  - id: Z1
    role: closure
    owner: root
    includes:
      - public / registry / consumer wiring still required
      - final diff-to-manifest check
      - required final-head validation
      - PR creation/update if requested

final_validation:
  - check: <repository-required integrated check>
    owner: Z1

operator_escalation_if:
  - <decision not owned by this policy>
```

The manifest is a compiled work order, not a miniature proposal. Do not spend
reasoning documenting choices that cannot affect execution, validation,
escalation, or resumption.

### Manifest revision

If evidence changes implementation mechanics while objective and authority stay
intact, perform a local recompile. Increment `manifest_revision` and record the
specific failed assumption or superseded unit. Do not silently mutate the plan.

A materially changed objective, acceptance contract, owner, safety boundary, or
operator-visible behavior is not a local recompile; escalate it.

## Phase 2 — establish the first complete slice

When work contains repeated or analogous units, implement one representative
slice before fan-out or delegation.

The slice must cross the boundaries that later work will rely on. Depending on
the task, that can include:

- internal implementation;
- wrapper/adapter behavior;
- registry or public dispatch;
- consumer/report/render behavior;
- focused tests through the documented public path.

Do not declare a pattern established merely because an internal module compiles
or an isolated unit test passes.

Record the accepted pattern only after the slice validates:

```yaml
pattern:
  id: <pattern-id>
  source_unit: A1
  status: accepted
  applies_when:
    - <boundary condition>
  procedure:
    - <repeatable transformation>
  validation:
    - <focused check>
  escalate_if:
    - <condition where pattern stops applying>
```

If the slice exposes wrapper loss, ownership mismatch, incompatible defaults,
public wiring problems, or another cross-boundary anomaly, revise the manifest
before continuing.

## Phase 3 — choose root execution vs delegation

After the first slice, classify the remaining work. The default is that the
root continues.

### Stay in the root context when

- the remaining work is small or tightly coupled;
- the root already holds nearly all information required to perform it;
- transferring the unit would duplicate substantial repository context;
- the root would immediately need to inspect or correct the child's work;
- useful parallel work does not exist while a child runs;
- the runtime requires repeated model-level polling to receive completion.

### Delegation viability gate

A child may be launched only when:

```yaml
delegation_viability:
  terminal_receipt_without_model_polling: true  # required
  materially_smaller_child_context: true | false
  useful_independent_parallelism: true | false
```

`terminal_receipt_without_model_polling` is mandatory. At least one of
`materially_smaller_child_context` or `useful_independent_parallelism` must also
be true.

If the gate fails, keep execution in the root context. Do not create delegation
solely to obtain a cheaper reasoning tier.

### Concurrency

Default `live_subordinates` is **1**. More than one requires a manifest note
showing that the units are independently validatable and that parallelism is
expected to outweigh duplicated context and integration cost.

There is no default coordinator role. Introduce an intermediate actor only if a
future task shows that it can *replace* substantial root synchronization rather
than add another live context.

## Worker dispatch contract

A delegated child receives the compiled unit, accepted pattern if applicable,
and only the repository context needed for that unit.

```yaml
policy: ad-hoc-implementation/v2
manifest_revision: 1
unit: A2
objective: <bounded transformation>
pattern: <pattern-id or null>
constraints:
  - <must preserve>
validation:
  - check: <focused check>
    owner: A2
escalate_if:
  - pattern does not apply cleanly
  - another owner/boundary appears
  - public behavior differs from the manifest assumption
  - validation exposes an unpredicted failure class
  - scope/product judgment is required
return_schema:
  - unit
  - manifest_revision
  - head
  - status
  - plan_fit
  - changed_files
  - validation
  - anomalies
  - evidence_refs
```

Do not send the root's reasoning transcript. Do not ask the child to narrate
routine progress.

## Terminal receipt contract

Normal success is one compact terminal receipt:

```yaml
unit: A2
manifest_revision: 1
head: <sha>
status: complete
plan_fit: matched
changed_files:
  - <path>
validation:
  - check: <identity>
    status: pass
anomalies: []
refs:
  diff: <ref>
  validation: <ref>
```

An invalidated work order returns an anomaly instead of broadening itself:

```yaml
unit: A2
manifest_revision: 1
head: <sha>
status: blocked
plan_fit: invalidated
anomalies:
  - summary: <failed assumption>
    evidence: <ref>
    decision_needed: <bounded decision>
recommendation: local_recompile | operator_escalation
```

Raw logs and long diffs remain addressable evidence. They do not enter the root
context unless the receipt is insufficient or contradictory.

## Synchronization

The normal delegated lifecycle is:

```text
dispatch once -> terminal receipt once -> release child
```

Do not repeatedly invoke a model merely to ask whether the child is finished.
Do not use progress prompts, stdin peeks, or sleep/wait loops as a substitute
for terminal receipt delivery.

If the available runtime cannot suspend the parent without repeated model
activations, delegation fails the viability gate and the work stays with the
root.

Allow at most one targeted clarification when a receipt is materially
ambiguous. Repeated clarification means the dispatch/return contract failed;
recompile or execute locally instead of drifting into supervision.

## Validation ownership

Every check in the manifest has one owner.

A successful focused check is not automatically rerun by the root. Re-run it
only when:

- later changes can invalidate that result;
- the check is explicitly designated as final-head/integrated validation; or
- repository guidance requires it at closure.

The root owns whole-delivery validation in Z1. Reduce deterministic output to
pass/fail/count/failing identities and evidence references where possible.

## Local recompilation

When repository structure or validation contradicts the manifest, raise
attention only for the affected boundary. Decide among:

1. local manifest revision;
2. execute the affected work directly;
3. issue a corrected bounded dispatch;
4. operator/proposal escalation;
5. abort invalid delivery.

Do not rebuild the entire plan unless the objective or authority itself was
wrong.

## Z1 — root-owned closure

After implementation units are complete, release any child and let the root
finish the deterministic tail:

1. reconcile completed units against the latest manifest revision;
2. finish remaining public/registry/consumer wiring that belongs to the
   delivery;
3. run only required final-head/integrated validation;
4. verify no anomaly or deferred authority decision remains;
5. verify the final diff stays within objective, constraints, and non-goals;
6. create/update the requested delivery artifact, such as a PR.

Do not launch another actor merely to perform closure.

## Completion

`ad-hoc-implementation/v2` is complete when:

- the bounded operator objective is implemented;
- all manifest units are complete or explicitly superseded by a recorded local
  recompile;
- required validation passes on the appropriate final head;
- the final diff remains inside the original authority and scope;
- no unresolved anomaly requires operator/proposal authority;
- the requested delivery artifact exists.

Completion does not require proving that no other improvement is possible.

## Escalate instead of continuing when

- the task becomes product-definition work;
- correctness depends on choosing among materially different user-visible
  behaviors without existing authority;
- an accepted external contract, safety boundary, schema, or ownership model
  must change;
- scope expands materially beyond the operator request;
- repeated local recompilation shows the task was not actually bounded;
- validation falsifies the initial understanding of the request.

## Trial metrics

Record enough information to evaluate topology, not just token totals:

```yaml
orchestration_metrics:
  model_calls:
    root: <count>
    children: <count>
  child_launches: <count>
  root_child_turns: <count>
  poll_wait_turns: <count>       # target: 0
  max_live_subordinates: <count> # default target: 1
  duplicated_validation: <count>
  manifest_revisions: <count>
  outcome: pass | fail | escalated
```

Token and cost measurements are useful when available, but a cache-heavy run
can hide structurally wasteful orchestration. Model activations, live contexts,
and duplicated work are first-class results.
